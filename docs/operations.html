FanHarvard LDCon operations

Still in active development. This is the site repository; Python implementation and tests belong to ldcon, experiment-core, experiment-drivers and agentbridge. The initial snapshot was reviewed from the October 30, 2026 configuration. It is not a live-state report.

Editable development

git clone https://github.com/FanHarvard/ldcon-fanharvard.git
cd ldcon-fanharvard
python3.12 ops/setup.py --editable
.venv/bin/python ops/site.py validate

Linux and Python 3.12 are the supported site environment. The setup tool creates .venv, clones the four public repositories at compatible tags or a pinned commit, creates a development branch, and installs all four with pip's editable mode. libraries/ is ignored by this repository: each library has its own Git history. Existing checkouts are reused without fetch, reset, checkout or deletion.

To reuse checkouts in another directory, add --libraries-root /absolute/library-parent. The directory must contain ldcon, experiment-core, experiment-drivers, and agentbridge; missing repositories are cloned. Use --venv /absolute/new-venv for a separate test environment.

# Equivalent editable installs after the clones exist:
.venv/bin/python -m pip install -c constraints.txt \
  -e libraries/experiment-core -e libraries/experiment-drivers -e libraries/agentbridge \
  -e 'libraries/ldcon[web,instruments,analysis,agents]'
.venv/bin/python -m pip list --editable

Python source edits take effect in newly started processes. Running processes keep loaded modules; service restart and hardware handover are separate operations. Changes to dependencies, entry points or package metadata require rerunning setup. If changing a package version, update the corresponding pins together.

Switching to published packages and back

python3.12 ops/setup.py --published
.venv/bin/python -m pip list --editable
python3.12 ops/setup.py --editable
.venv/bin/python -m pip list --editable

Published mode explicitly reinstalls the pinned distributions from PyPI and GitHub (including the SHA-256-checked DHO wheel), so a same-version editable installation does not remain active. Library checkouts and their edits remain on disk. Switching back reuses them. Do not run either mode against the virtualenv of a running deployment. Use another --venv and review its configuration before a planned cutover.

init requires a new directory outside this repository and refuses to overwrite existing state. It expands ${STATE_ROOT} paths, validates the three laser assignments and owner policies, and creates local credentials. plan prints commands; units writes user-systemd drafts. Neither starts, enables, installs or restarts a service. Unit drafts use the interpreter that runs the command; regenerate them after selecting a different virtualenv. Fresh dashboard capability URLs are generated only when Web starts.

The clone contains no existing hardware authority: retain/review the actual local commissioning evidence, physical-lock manifest and inode identities, existing leases and owner state during migration. Set LDCON_PHYSICAL_LOCK_MANIFEST in local.env to the verified host manifest (default draft path: STATE_ROOT/private/physical-locks.json). Do not invent a new manifest to bypass an existing owner. Source evidence files are not distributed; reviewed local copies go under private/evidence/. Review the existing per-device allow_output/writes_enabled values before enabling hardware.

The site snapshot names the installed digital-servo driver and exact hardware identities; the reusable LDCon library is not tied to one board. Other boards require a compatible adapter and commissioning. External wavemeter, telemetry/metrics and instrument firmware services remain separate dependencies.

Agent execution requires the selected provider CLI/login, Linux bubblewrap and the necessary host user-namespace support. Supported resident clients are Claude Code, Codex and OpenCode, with DeepSeek Harness as a task adapter. Host-only credentials and adaptive-control authority are hidden from agent sandboxes. No prior sessions, hub registrations, messages or notification destinations are imported by init; every new agent needs its own verified identity. Notification destinations are configured locally.

Updating and eventual cutover

  1. Commit library edits in their own repositories. Test and publish compatible library releases, then update requirements.txt, constraints.txt and the tags in ops/setup.py together.
  2. Review site configuration changes in this repository. Runtime configuration is a copy: Git pull does not silently overwrite settings saved by operators or agents. Bring selected non-secret changes back into site/, replace the local state-root prefix with ${STATE_ROOT}, clear session/artifact pointers and keep initial outputs disabled.
  3. Clone the approved site commit into a new directory, create a new environment and a new staging state root, then validate and review generated units. For production, use published wheels and record the site commit, package versions, pip freeze and configuration hashes. Keep that release immutable.
  4. Before any physical cutover, inspect current jobs, output readbacks, faults, ownership, retained leases and commissioning records. Preserve the existing physical-lock exclusion domain and credential identity; freshly generated staging keys do not authenticate to existing owners. Review config differences against the actual installed release.
  5. Use the established normal stop/hold and owner handover procedure in the site's normative deployment design (§7.1). Shared instruments require their consumers and leases to be handled in the defined order. Promote a consistent release across roles; retain the previous release, configuration and units for rollback. Do not restart owners during a lock or discard durable state to make startup pass.

This repository preparation performs no live migration. The current source at /opt/ldcon/repo/ldcon/doc/card-system-design.md remains the host's normative design; changing repository layout does not change its operating constraints.
